# 1. 层和块

## 1.1 Module、Sequential 与 forward

Module 将可学习状态和计算组织成可组合单元；forward 描述数据如何流动。Sequential 适合单输入、顺序串联的网络，包含分支、跳连或多个输入时应显式编写 forward。

![模块树与实际数据流](/modules-tree.png)

图中的树表示“谁拥有谁”，并不自动决定执行顺序。一个子模块可以在一次前向中被调用多次，也可以有条件地不被调用。模块边界应对应可独立理解、验证和复用的功能。

## 1.2 ModuleList、模块树与组合

ModuleList 管理子模块注册，但不替你定义前向；普通 Python 列表中的模块可能不被父模型发现，导致参数无法被统一移动、保存或交给优化器。

ModuleDict 适合具名分支。组合模型时先约定输入输出形状、掩码和 dtype，再讨论内部实现；只有“能运行”而没有接口契约，后续替换模块很容易破坏语义。

# 2. 参数管理

## 2.1 Parameter、buffer 与注册

Parameter 通常表示优化器可见的可学习张量；buffer 保存非参数状态，例如 BatchNorm 的运行均值。持久 buffer 会随 state_dict 保存，并随模块迁移设备；普通张量属性没有同样的自动管理保证。

![可学习参数与持久状态](/modules-state.png)

图中两类状态都可能出现在权重文件中，但只有需要梯度且被优化器管理的参数会更新。检查模型时同时查看 named_parameters 和 named_buffers，避免只数参数却遗漏运行状态。

## 2.2 初始化、共享与冻结

参数共享意味着多个计算路径引用同一个参数对象，各路径梯度相加。复制相同初值则只是初始数值相同，后续可以独立变化。初始化必须在训练前完成，避免加载检查点后又把权重覆盖。

![同一权重的共享与停止参数更新](/modules-sharing.png)

冻结权重只表示不更新它，输入梯度仍可能需要穿过该层。把整段前向放入 no_grad 会连输入路径一起截断，对前面仍需训练的模块可能是错误的。

# 3. 自定义层

## 3.1 形状契约与可微计算

自定义层先写明接口，例如 [B,T,D] → [B,T,D]，再写广播和归约轴。实现应尽量由已有可微张量运算组合，让自动微分处理导数。

需要学习的张量应注册为 Parameter，固定常量可注册为 buffer。不要在每次 forward 临时创建一组新的“权重”；优化器跟踪的是初始化时传入的参数对象。跨 CPU/GPU 的隐式转换也应避免。

## 3.2 自定义模块与单元验证

有意义的单元验证包括：多种 batch 大小的形状；与朴素参考实现的数值一致性；梯度检查；序列掩码是否阻止无效位置影响结果；保存再加载后是否复现输出。

不要只测试输出“不报错”。例如归一化层应在选定轴上验证均值和方差，残差层应检查维度匹配，注意力层应检查被屏蔽位置不会贡献权重。随机层的测试需要固定随机源或比较统计性质。

# 4. 加载和保存模型／张量

## 4.1 state_dict 与训练检查点

state_dict 保存模型参数与持久 buffer。完整训练恢复还需优化器、调度器、训练步数、随机状态以及适用时的精度缩放状态。数据采样器位置也可能影响精确续训。

![恢复训练所需状态](/modules-checkpoint.png)

图中“仅保存权重”适合推理初始化，“保存训练状态”适合续训；二者用途不同。保存最佳模型时应写入独立快照，避免仅保留对一个仍在变化的对象的引用。

## 4.2 恢复训练、版本与权重加载

加载时明确设备映射与架构版本；推荐先在 CPU 上读取，再将模型放到目标设备，便于控制峰值显存。检查 missing keys 和 unexpected keys，不能用宽松加载静默掩盖结构错误。

PyTorch 的受限 weights_only 加载面向张量和简单容器，复杂对象检查点可能需要额外处理。只加载可信来源的文件，并保存配置与词表等外部状态。当前行为以 [torch.load 官方说明](https://docs.pytorch.org/docs/stable/generated/torch.load) 为准。

# 5. GPU

## 5.1 设备、数据类型与张量迁移

模型和输入需要位于兼容设备。移动模块后再建立优化器，是较清晰的组织方式；分类索引不应因为模型使用低精度浮点而一起转成浮点标签。

数据搬运可成为瓶颈。页锁定内存与非阻塞复制只有在硬件、流和数据管线配合时才可能产生重叠；小批量频繁搬运通常难以充分利用 GPU。先测吞吐，再判断是不是算力不足。

## 5.2 异步执行与正确计时

GPU 通常异步执行：CPU 提交操作后立即继续，普通计时器可能只测到提交时间。计时应使用 CUDA event 或在边界同步，并在预热后重复测量。

![异步提交、同步计时与编译](/modules-gpu.png)

图中计时区间结束于 GPU 完成，而不是 CPU 提交结束。读取标量到 CPU、打印 GPU 张量、频繁同步都可能打断流水线；性能分析时把这些调试操作与核心计算分开。

# 6. 现代执行工具

## 6.1 torch.compile 与图中断

torch.compile 尝试捕获计算并优化执行，图中断会把执行分成较小片段。动态形状、数据依赖的 Python 控制流和部分副作用可能影响捕获；首次编译成本与稳定运行成本应分别报告。

编译前先确保 eager 模式正确，然后在相同输入上比较数值与性能。形状不断变化时，还需记录重编译次数；不能只挑一个固定长度的最佳数字作为整体收益。参见 [PyTorch 编译文档](https://docs.pytorch.org/docs/stable/torch.compiler.html)。

## 6.2 混合精度、导出与部署边界

混合精度控制算子的执行类型，导出把模型转换为部署系统可理解的图；二者都不自动保证任务质量不变。导出时需定义动态维度、输入范围和支持的算子集合。

部署验收同时看数值误差、任务指标、峰值显存、冷启动和稳态时延。把预处理、模型、后处理作为一个整体版本化，才能避免“权重相同但线上结果不同”的问题。

## 综合算例：冻结层仍传递梯度

设 $u=ax$，$y=bu$，其中 a 可训练、b 冻结。虽然不更新 b，仍有 $\partial y/\partial a=bx$。如果对 b 所在前向使用 no_grad，u 到 y 的图被截断，a 也失去这条学习信号。

因此“冻结某层”应先考虑上游是否还有可训练模块。仅做纯特征提取且上游也无需训练时，关闭该段图才是合适优化。

## 保存加载的验收

固定一组输入，切到 eval 模式，记录保存前输出；新建同配置模型，加载 state_dict，再比较输出。随后恢复完整训练状态，比较下一步学习率与参数更新。前一个检查验证推理复现，后一个检查验证续训，两者不能互相替代。
