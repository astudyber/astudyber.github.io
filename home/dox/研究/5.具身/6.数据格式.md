# 1. 数据格式：让一条轨迹能够独立解释

## 1.1 概览

机器人数据不能只看成“视频 + 一串数字”。它必须能回答：机器人当时看到了什么、处于什么状态、接收了什么命令，以及执行后发生了什么。本篇给出学习用的数据契约，并对照 RLDS 与 LeRobot；示例字段不是二者的直接兼容标准。资料核对日期：2026-09-21。

![机器人 episode 的相机、状态、控制命令时间轴及数据表、视频、元数据](/data-schema.png)

图为 AI 辅助教学示意。三行位于同一时间轴，强调语义上的对齐；真实传感器频率通常不同，不能只按数组下标拼接。

# 2. Episode、Step 与 Transition

## 2.1 三个基本单位

- Episode：从一次任务开始到结束的一段完整记录。
- Step：一个时间点的观测、状态、动作及其他字段。
- Transition：用于学习状态变化的关系，常写成 $(o_t,a_t,r_t,o_{t+1})$。

必须规定 $a_t$ 是在读取 $o_t$ 后下发的命令，还是此前已经执行的命令。两种记录习惯都可能存在，但训练样本构造不能混用。

## 2.2 状态不等于动作

假设实测关节角为 0.2 rad，控制器收到目标 0.3 rad，此刻机器人未必已经达到 0.3 rad。“测量状态”和“下发目标”应该分别存储。直接把下一帧测量状态当动作标签，可能引入伺服延迟与控制模式差异。

| 字段组 | 示例 | 必须写清的语义 |
| --- | --- | --- |
| 观测 | RGB、深度、触觉 | 相机名称、采集时间、编码 |
| 本体状态 | 关节角、速度、夹爪宽度 | 字段顺序、单位、参考系 |
| 动作 | 目标角、末端增量 | 绝对或相对、控制频率 |
| 任务 | 指令、任务标识 | 子任务或全局任务 |
| 结果 | 成功、失败、超时 | 判定条件和判定时刻 |

# 3. 常用组织方式

## 3.1 RLDS：保留 episode 与 step 结构

RLDS 定义 episode、steps 和相应元数据，并使用 is_first、is_last、is_terminal 等字段描述轨迹边界。最后一帧存在，并不意味着它还有一个可执行的下一动作；应遵循该数据集的字段有效性约定。参见 [RLDS 官方说明](https://github.com/google-research/rlds)。

## 3.2 LeRobotDataset：表格、视频和元数据协作

LeRobotDataset v3 使用表格记录数值数据，并通过元数据定位视频和 episode。在较大规模下，一个物理文件可以容纳多段 episode；“一个 episode 一个文件”不是通用前提。使用转换器时锁定数据格式版本与库版本。参见 [LeRobotDataset v3 文档](https://huggingface.co/docs/lerobot/lerobot-dataset-v3)。

## 3.3 HDF5 与 Zarr

HDF5、Zarr 更接近多维数组的容器方案，不自动规定 action 的物理含义。选择容器时考虑分块读取、压缩、并发和已有工具；无论用哪一种，都要单独定义数据契约。参见 [HDF5 文档](https://support.hdfgroup.org/documentation/hdf5/latest/) 与 [Zarr 文档](https://zarr.readthedocs.io/en/stable/)。

# 4. 一个可解释的教学样例

## 4.1 Episode 元数据

下面是假设的末端增量控制数据；数值用于说明字段，不是实际采集记录，也不是可直接加载的 LeRobot 文件。

```json
{
  "schema_version": "teaching-1",
  "episode_id": "pick_cup_0001",
  "robot_id": "arm_a",
  "task": "把杯子放到托盘中",
  "control_hz": 20,
  "action_space": "eef_delta_base",
  "action_fields": ["dx", "dy", "dz", "rx", "ry", "rz", "gripper"],
  "translation_unit": "m",
  "rotation_representation": "rotation_vector",
  "rotation_unit": "rad",
  "gripper_encoding": "0=open, 1=close",
  "calibration_version": "calib_001",
  "success": true,
  "termination_reason": "task_complete"
}
```

eef_delta_base 在这个例子中表示平移增量用基座坐标表达；旋转增量采用旋转向量。还必须在项目协议中写明旋转左乘或右乘、夹爪命令的保持方式，以及动作作用的时间区间。

## 4.2 Step 的信息

一个 step 至少关联观测时间、各传感器原始时间、当前状态、命令下发时间和动作。多相机异步时，保存每路时间戳及匹配误差；不要为了得到相同长度而静默丢帧。

终止信息建议同时保留原因。例如成功完成、物理失败、人工停止和达到时间上限应分开，避免后续把所有结束都当作失败。

# 5. 动作块与掩码

假设一条轨迹有 $T$ 个有效动作，训练从 $t$ 构造长度为 $H$ 的动作块。尾部只有 $T-t$ 个动作时，可填充到固定长度，但必须提供有效位置掩码：

$m_k=\mathbf{1}[t+k<T]$，其中 $0 \leq k < H$。

训练损失只聚合有效位置。否则模型会把人工补齐的“全零动作”当作真实行为。跨本体的无效动作维度同样需要维度掩码，不能靠补零表示“这个关节不存在”。

# 6. 校验与版本管理

## 6.1 入库前检查

1. 文件可解码，字段齐全，数值有限。
2. 时间戳单调；重复时间与丢帧有明确处理记录。
3. 动作单位、坐标、夹爪符号与控制接口一致。
4. Episode 边界正确，不把前一任务的尾帧接到下一任务。
5. 抽样同时回放视频、状态和命令曲线。

## 6.2 转换后检查

转换不是“能被加载”就算成功。比较转换前后 episode 数、有效步数、时间长度、动作范围及随机样本；对元数据和原始文件记录校验值。归一化统计与训练划分绑定，字段顺序或单位改变必须升级版本。

推荐把原始数据、转换配置、划分清单、统计量与模型检查点一起建立关联。这样发现符号错误时，能定位受影响的训练，而不必猜测哪些模型用了哪一批数据。


# 扩展图解：接口、机制与实验

## 1. 观测、命令与响应的时间

![观测、命令与响应的时间](/data-time.png)

一条控制链至少存在采集时间、命令下发时间和响应时间。视频帧的保存顺序不能替代物理时间；网络排队和编码也可能引入不稳定延迟。

图中命令发出后状态才变化，因此用下一帧状态代替当前动作需要额外假设。建议保留原始时钟、同步映射和对齐误差，转换时明确动作对应哪个观测以及哪个执行区间。

## 2. 坐标与旋转约定

![坐标与旋转约定](/data-frames.png)

上方连线表示标定关系；坐标映射方向以矩阵上下标为准。公式中的点使用齐次坐标，相机光学坐标轴约定须另行声明。

末端位移可以在基座系或工具系表达；相同数值在不同坐标系中对应不同方向。刚体变换写作 $T^A_B$ 时，应明确它把 B 系坐标映射到 A 系，复合顺序必须一致。

图中相机、基座和工具都需要标定关系。旋转还需声明四元数顺序、是否归一化、欧拉角顺序或旋转向量约定；这些字段变化应升级数据版本，不能仅修改注释。

## 3. 动作块的有效位置

![动作块的有效位置](/data-mask.png)

尾部动作块长度不足时，填充值只是形状占位，不能作为监督。时间掩码排除越界时刻，维度掩码排除该机器人不存在的动作维度；两者相乘才得到有效元素集合。

图中的损失应除以有效元素数。若分母仍按完整块大小计算，尾部样本会被无意降权。全无效样本应跳过或明确处理，避免除零和虚假的零损失。

## 4. 数据契约与版本追踪

![数据契约与版本追踪](/data-version.png)

图中的配置值、统计量和版本号都是示例。机器人图像不能随意水平翻转：仅在同步变换动作、坐标及相机几何且任务语义保持时才可采用。

可复现数据集需要同时记录原始文件、schema、转换参数、划分清单和归一化统计。模型检查点应能追溯到这组版本，而非只记录一个会被覆盖的目录名。

图中的每条连线都是依赖关系。发现夹爪符号错误时，可沿依赖找到受影响模型；修复后生成新版本并重新校验，不应直接覆盖旧数据却保留原版本号。
